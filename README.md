## 1. Executive Overview & Key Highlights

### Core Capabilities at a Glance

- **Authoritative Corpus (16,200 Documents / 17,412 Chunks)**:
  - **Phase 1**: 2,500 enterprise email threads across seven business domains and six source systems.
  - **Phase 2**: 13,700 publication-grade business PDFs across 16 distinct layout blueprints (~673 MiB), generated from canonical warehouse records with 100% field grounding, valid signatures, and authorized partner logos.
  - **Zero Failures**: Validated 1:1 parity between PostgreSQL tracking records and Qdrant vector points.
- **Ultra-Fast 3-Node Orchestration**:
  - Replaced legacy multi-LLM sequential fan-out (which suffered from 15–48s latency) with a lean 3-node LangGraph topology: **Deterministic Routing $\rightarrow$ Parallel Evidence Gathering $\rightarrow$ 1-Call Bounded Synthesis**.
  - **Zero LLM Calls** for purely structured database lookups via deterministic semantic query compilation.
  - Sub-3-second warm response latency (**p50: 2.528s, p95: 3.254s**).
- **Guarded Analytics Engine**:
  - Eight curated PostgreSQL analytical views backed by AST-enforced, read-only SQL compilation.
  - Gemini is strictly restricted to proposing a structured `BusinessQueryPlan` JSON object; **Gemini never generates executable SQL syntax directly**.
- **Deterministic Claim Verification**:
  - Atomic claims generated by Gemini are validated against retrieved evidence using strict regular expressions for business identifiers (`PO-...`, `CON-...`, `INV-...`, `FCIU...`), numeric normalization via Python `Decimal`, and date matching.
  - Unsupported claims are withheld locally before reaching the user; no second LLM call is wasted on text rewriting.
- **Hardware-Accelerated Local Inference**:
  - Pinned ONNX Runtime CUDA 12 / cuDNN 9 execution provider on Windows host (tested on NVIDIA GeForce GTX 1650), yielding **0.059s** warm vector retrieval and **1.867s** warm reranking. Silent CPU fallbacks are strictly rejected at startup.
- **Build-Free Responsive Web Interface**:
  - Pure HTML5, modern CSS, and native JavaScript ES modules served directly by FastAPI from a single origin. Zero Node.js, npm/pnpm, or bundling dependencies.

## 2. Quick Start & Developer Runbook

### Local Prerequisites

- **Operating System**: Windows 10/11 or Linux.
- **Docker Desktop**: Running with Compose v2 enabled.
- **Python**: Version 3.12 managed within a Conda environment named `SKOPE`.
- **LLM API Key**: An active Google Gemini API key with access to `gemini-3.5-flash-lite`.
- **Hardware**: NVIDIA GPU (e.g., GTX 1650 or higher) with CUDA 12.x / cuDNN 9.x for acceleration, or explicit CPU mode.

### Release Assets and Dataset Placement

The Git repository intentionally excludes credentials, model caches, Docker volumes, and the 16,200-document synthetic corpus. Download these files from the repository's [Releases page](https://github.com/sanmitra-b/SKOPE---Supply-Chain-Knowledge-and-Operations-AI-engine/releases):

- `RAG-Project-Dataset.zip` — the complete synthetic source corpus.
- `skope-postgres.dump` — a portable PostgreSQL custom-format archive.
- `skope_chunks_v1.snapshot` — the matching Qdrant 1.19 collection snapshot.
- `SHA256SUMS.txt` — checksums for all release assets.

Place the downloads in `release-assets/`, verify their SHA-256 values against `SHA256SUMS.txt`, and extract the corpus:

```powershell
Get-FileHash .\release-assets\RAG-Project-Dataset.zip -Algorithm SHA256
Expand-Archive .\release-assets\RAG-Project-Dataset.zip -DestinationPath .
```

After extraction, this path must exist:

```text
SKOPE/RAG Project Dataset/harmonized_data
```

### Environment Setup

Create the local configuration file:

```powershell
Copy-Item .env.example .env
```

Set `GEMINI_API_KEY` in `.env`. The supplied defaults use local development authentication, the Docker PostgreSQL credentials, `skope_chunks_v1`, and CPU inference. To use the verified NVIDIA path, install the optional GPU dependencies below and change `EMBEDDING_EXECUTION_PROVIDER` to `CUDAExecutionProvider`.

### Dependency Installation

```powershell
conda create -n SKOPE python=3.12 -y
conda activate SKOPE
python -m pip install -r database/requirements-app.txt
```

Optional NVIDIA CUDA acceleration on Windows:

```powershell
python -m pip install -r database/requirements-gpu-windows.txt
```

The first retrieval request downloads the BGE embedding and reranking models into the ignored `.model-cache/` directory.

### Infrastructure Launch

```powershell
docker compose up -d postgres qdrant
docker compose ps
```

Qdrant is pinned to version 1.19.0 because collection snapshots are version-sensitive.

### Option A — Fast Restore from Release Snapshots

Use this path to reproduce the demonstrated 1.32-million-row database and 17,412-point vector index without rebuilding them. These commands replace the contents of a matching local SKOPE database/collection, so use fresh Docker volumes or back up anything important first.

```powershell
docker cp .\release-assets\skope-postgres.dump skope_postgres:/tmp/skope-postgres.dump
docker exec skope_postgres pg_restore --clean --if-exists --no-owner --no-privileges -U skope_admin -d skope_db /tmp/skope-postgres.dump

curl.exe -X POST "http://localhost:6333/collections/skope_chunks_v1/snapshots/upload?priority=snapshot" -H "Content-Type: multipart/form-data" -F "snapshot=@release-assets/skope_chunks_v1.snapshot"

python scripts/validate_index.py
```

Successful validation reports exactly **16,200 source documents**, **17,412 PostgreSQL chunks**, **17,412 Qdrant points**, zero failed documents, and `"valid": true`.

### Option B — Full Rebuild from the Dataset

Use this path to reproduce the ETL, extraction, chunking, embedding, and indexing process itself:

```powershell
python scripts/ingest_to_db.py --rebuild
python scripts/apply_app_schema.py
python scripts/apply_analytics_views.py
python scripts/reconcile_and_validate.py
python workers/ingestion/ingest_corpus.py --full --collection skope_chunks_v1 --rebuild
python scripts/validate_index.py
```

The full rebuild is substantially slower because all 16,200 documents must be extracted, chunked, embedded, and indexed locally.

### Running the Application

Launch the unified FastAPI server:

```powershell
python scripts/run_api.py
```

- **Web Workspace**: Open [`http://localhost:5173`](http://localhost:5173) in your browser.
- **Login**: In `dev` mode, enter the token configured in `DEV_AUTH_TOKEN` (e.g., `skope-local-developer-key-2026`).
- **Interactive OpenAPI Documentation**: Available at [`http://localhost:5173/docs`](http://localhost:5173/docs).

### Test Suite & Benchmark Evaluation

Run the automated test regressions:

```powershell
python scripts/run_tests.py
```
*(Expected: 71 tests passing, 0 errors)*.

Run the curated 50-question evaluation benchmark:

```powershell

python scripts/run_evaluation.py --include-sql

# Fast smoke checks

```

Run the end-to-end benchmark recording stage latencies, citations, and claim support rates:

```powershell
python scripts/run_end_to_end_benchmark.py
```

### Docker Containerized Packaging

To build and run the entire stack (PostgreSQL, Qdrant, and the CPU-mode FastAPI application serving the vanilla frontend) within Docker:

```powershell
docker compose up -d --build
```
Access the application directly at `http://localhost:5173`.

## 6. Structured Operational Data & Analytics Engine

### Relational Schema Design

The PostgreSQL database (`skope_db`) hosts both historical operational data (Phase 1) and procurement/compliance entities (Phase 2):

- **Phase 1 Operational Warehouse**:
  - `dim_customer` (54,792 rows), `dim_product` (34,581 rows), `dim_location`, `dim_partner`
  - `fact_order_fulfillment` (415,693 rows), `fact_freight_movement`, `fact_inventory_event` (65,192 rows), `container_tracking` (1,545 rows)
  - `restricted.customer_contact`: Dedicated schema storing sensitive customer contact details. Strictly segregated from the default `skope_rag_reader` role.
- **Phase 2 Enterprise Procurement & Logistics**:
  - `supplier` (30 vendors) & `supplier_product` (600 relationships)
  - `purchase_order` (1,600 POs) & `purchase_order_line` (4,800 lines)
  - `shipment` (1,200 records), `shipment_container` (1,200 links), `goods_receipt` (4,800 receipts)
  - `contract` (300 contracts) & `contract_clause` (1,500 clauses)
  - `warehouse_audit` (100 audits) & `audit_finding` (300 findings)
  - `customs_entry` (200 filings) & `enterprise_policy` (50 SOP policies)

> **Total: 1,321,826 source records across 20+ relational tables** (Phase 1 operational warehouse + Phase 2 enterprise procurement & logistics)

### The 8 Curated Analytics Views

To ensure high performance and prevent arbitrary table joins, all analytical queries run against pre-optimized, verified views:

1. `v_supplier_performance_summary`: On-time delivery rate, total orders completed, defect count, average fulfillment lead time.
2. `v_open_purchase_orders`: Unfulfilled PO lines, committed quantities, supplier identifiers, expected delivery dates.
3. `v_shipment_delay_profile`: Carrier transit durations, port congestion variances, recorded delay codes.
4. `v_container_tracking_status`: Live container locations, vessel IDs, voyage numbers, seal numbers, clearance status.
5. `v_current_inventory_status`: Stock on-hand, reorder thresholds, allocated volumes across plants and dark stores.
6. `v_contract_sla_terms`: Active contracts, penalty percentages, free-day allowances, demurrage rates, liability caps.
7. `v_material_shortage_analysis`: Quantity variances between purchase orders and actual goods receipts, root-cause tags.

### Semantic Query Planning & Deterministic SQL Compiler

Instead of allowing Gemini to write freeform SQL, SKOPE uses a two-tier compiler:

1. **Local Intent Planning**: Standard user intents (e.g., *"Which suppliers have open purchase orders?"*) map directly to a typed `BusinessQueryPlan` in Python.
2. **Schema-Constrained Fallback**: For unfamiliar analytical queries, Gemini receives an enum-constrained JSON schema. It can only specify allowlisted dataset names, dimensions, measures, and filter operators.
3. **Deterministic Compilation & AST Guard**:
   - The Python compiler translates the `BusinessQueryPlan` into standard SQL.
   - The generated query is parsed with `sqlglot` to enforce an AST allowlist: only `SELECT` and `CTE` constructs are allowed.
   - Execution is restricted to a read-only transaction with a **5-second statement timeout** and a hard row limit.

```python
# Sample BusinessQueryPlan generated without LLM SQL syntax generation
plan = BusinessQueryPlan(
    dataset="open_purchase_orders",
    dimensions=["supplier_name", "po_id"],
    measures=["total_open_lines", "total_committed_qty"],
    filters=[TypedFilter(field="order_status", op="EQ", value="OPEN")],
    sort_by=["total_committed_qty"],
    sort_desc=True,
    limit=50
)
```

## 8. Hybrid Retrieval & Vector Engine

SKOPE employs a multi-stage retrieval architecture that combines lexical precision, semantic recall, and neural reranking:

```
  Incoming Query
        │
        ├── [Stage 1: Exact-Identifier Extraction]
        │     - Matches explicit PO, Contract, Container, Invoice, or Product IDs
        │     - If all requested entities are resolved -> RETURN EXACT EVIDENCE IMMEDIATELY
        │       (Bypasses dense search, sparse search, and neural reranking)
        │
        └── [Stage 2: Qdrant Hybrid Retrieval]
              ├── Dense Vector Search (BAAI/bge-base-en-v1.5, 768 dimensions)
              └── Sparse Lexical Search (Qdrant BM25 sparse vectors)
                    │
                    ▼
              [Stage 3: Reciprocal Rank Fusion (RRF)]
                    │
                    ▼
              [Stage 4: Bounded Neural Reranking]
              - BAAI/bge-reranker-base evaluated on top 8 to 12 candidates
              - Evaluated only when semantic ambiguity warrants precision lift
                    │
                    ▼
              Top 6 to 8 Verified Chunks Returned to Orchestrator
```

### Layout-Aware Chunking Strategies

Rather than applying a fixed character sliding window, SKOPE uses layout-specific chunking parsers:
- **Contracts**: Chunked by clause and section headers (`Section 4.2: Late Delivery Penalties`), preserving governing law, supplier ID, and contract ID in chunk metadata.
- **Invoices & Purchase Orders**: Header metadata chunk (supplier, customer, dates, totals) plus line-item table chunks.
- **Manifests & Bills of Lading**: Maritime routing header (ports, vessel, voyage) plus container and seal allocation chunks.
- **SOPs & Audits**: Section-bounded chunks maintaining parent document hierarchy.
- **Emails**: Thread-level summary metadata chunk followed by individual message chunks retaining sender role and timestamps.

### Verified Hardware Acceleration (CUDA 12 / cuDNN 9)

SKOPE includes native Windows GPU support via ONNX Runtime:
- Preloads packaged CUDA runtime (`cudart64_12.dll`), cuBLAS (`cublas64_12.dll`), and cuDNN (`cudnn64_9.dll`) DLLs before session initialization.
- Startup health checks verify that `CUDAExecutionProvider` is active. Silent fallback to CPU is strictly rejected if CUDA is requested.
- **Benchmark Lift**:
  - Warm CPU Hybrid Retrieval + Reranking: **6.400s**
  - Warm GPU Hybrid Retrieval + Reranking: **1.867s**
  - Warm GPU Hybrid Retrieval (without Reranker): **0.059s**

## 9. Deterministic Claim Verification & Safety Guardrails

### The Evidence Contract

Every material factual claim returned by the system must link to at least one evidence object:
1. `document`: Document ID, chunk ID, page number, section name, exact excerpt, and source file URI.
2. `sql`: Query ID, executed SQL text, result rows, referenced views, and `data_as_of` timestamp.
3. `derived`: Explicit formula, inputs, and referenced evidence IDs for calculated values.

### Deterministic Claim Verification Engine

Before a synthesized claim is rendered in the final user response, it passes through strict Python verification:

```python
# Core logic of the deterministic claim verifier
def verify_claim(claim: AtomicClaim, evidence_items: List[Evidence]) -> bool:
    # 1. Verify cited evidence ID exists in retrieved set
    if not all(eid in evidence_index for eid in claim.evidence_ids):
        return False
        
    # 2. Extract and verify exact business identifiers (e.g. CON-P2-0101)
    business_ids = extract_business_identifiers(claim.text)
    for bid in business_ids:
        if not identifier_present_in_cited_evidence(bid, claim.evidence_ids):
            return False
            
    # 3. Extract and verify standalone numeric values using Decimal normalization
    numbers = extract_standalone_numbers(claim.text)
    for num in numbers:
        if not numeric_value_supported_by_evidence(num, claim.evidence_ids):
            return False
            
    return True
```

### Specific 4-State Abstention Framework

If the pipeline cannot verify an answer, it never hallucinates. Instead, it returns one of four explicit abstention states:

1. **`NO_EVIDENCE_RETRIEVED`**: No relevant documents or database records matched the query parameters.
2. **`INSUFFICIENT_EVIDENCE`**: Evidence was retrieved, but it lacks the specific facts required to answer the question.
3. **`VERIFICATION_FAILED`**: The reasoning model proposed an answer, but its claims failed deterministic identifier or numeric verification.
4. **`PROVIDER_UNAVAILABLE`**: The external LLM exceeded its 10-second request budget or triggered the circuit breaker.

### Enterprise Security Controls

- **Role-Based Access Control (RBAC)**:
  - `Operations User`: Standard chat, permitted document view, operational reports.
  - `Manager / Director`: Executive summaries, cross-facility performance scorecards.
  - `Administrator`: Index status, ingestion trigger, evaluation metrics, review queue.
  - `PII Operator`: Dedicated role required to access the `restricted.customer_contact` schema.
- **Prompt Injection Defenses**:
  - Retrieved documents and user inputs are strictly treated as data payloads.
  - System prompts reject any document content that attempts to alter instructions or escalate privileges.
- **Rate Limiting & Auditing**:
  - In-memory rate limiting per user and IP.
  - Full structured audit logging for all SQL executions, document retrievals, and administrative reviews.
